## 交付结果

  420 名行业员工。新增第 431 名「巡店经理」，拥有独立职责、能力、

  协作、行业老板管理看板。它们均是可持久化、可恢复、可审计的业务流，
  不是孤立展示页或一次性聊天。
- 数据库版本从 schema50 升级为 schema51，保留旧任务兼容，旧任务只在
  首次继续沟通时由服务端惰性收养，不对历史数据做高风险全表改写。

## 切片 A：连续多轮协作

- 新增 `task_thread` 链路和 `task.thread_id/revision_no/phase/request_key`
  字段；每一轮是不可变的新任务版本，上一版产出只由服务端取得并以
  有界上下文传入。
- 新增 `POST /api/tasks/{id}/followups` 和
  `POST /api/task-threads/{id}/accept`；前端在员工任务入口展示版本
  时间线，支持第 2/3/4 轮乃至继续迭代，满意后显式验收。
- `request_key` 幂等、事务 CAS 和部分唯一索引共同保证一条线程最多
  一个活动叶子；双击、超时重放和并发继续不会分叉或重复扣点。
- 新轮按一次真实工作计费；同轮失败沿用既有免费重试/退款链，不会
  将重试误计为新一轮。
- 首轮派活和后续修订都持久化 request key；服务端按完整输入校验重放，
  即使补充材料超过上下文截断长度也不会把不同请求误当成同一单。当前新轮
  免费重试耗尽时，可从最近一版成功交付继续或直接验收该版，失败版本仍保留
  在时间线上，不会让协作链永久卡死。
- 430 名通用文本直接派活员工走版本线程；巡店经理因必须保留照片
  证据和人工验收，以“整改 → 复查 → 通过/驳回”持续协作，不走无照片
  的通用文本继续接口。

## 切片 B：巡店经理闭环

- 新增门店、巡店、照片、问题、证据、整改、复查和事件表，所有业务记录
  都同时受 tenant 和 industry 范围约束。
- 支持门店建档、1～8 张现场图片、视觉分析、可见问题与照片证据绑定、
  严重度/置信度、整改责任人和期限、复查照片、AI 建议以及企业主人工
  通过/驳回。
- 区域经理可在自己获准行业建店；企业主可用版本 CAS 确认/修改实际责任人、
  期限和整改计划。工作台提供区域汇总、风险优先门店、门店筛选、每次巡店
  独立照片编号、整改前后照片分区和结构化操作时间线。
- 模型只能引用本次所属照片作为问题证据；低置信度项要求人工核查，
  AI 无权自动关闭整改项。
- 图片入库前执行类型/魔数、尺寸、容量、解码与重编码检查，移除 EXIF；
  单图不超过 8MB、一次 HTTP 上传总量不超过 38MB，任一文件失败则
  全部清理，不留半成品。
- 图片读取除租户校验外再校验巡店行业权限；路径必须在授权根目录内、
  必须是受管数据库记录且不允许符号链接越界。
- 巡店创建、重试、复查、整改状态均有幂等/CAS 门禁；超时、进程重启和
  启动失败有可恢复或原子退款路径。

## 切片 C：行业老板管理看板

- 新增只读范围、摘要和员工下钻 API。企业 owner 由服务端锁定本 tenant
  和 `tenant_industry` 显式行业；普通 member 拒绝；只有平台命名 Boss
  可显式切换企业/行业。
- 看板返回任务量、完成/失败/活动状态、平均交付时长、员工效率、风险、
  趋势、最近活动以及巡店与整改汇总；列表分页并批量补充员工元数据，
  2,000 条数据规模下的查询契约不超过 20 次，不做 N+1。
- 任务和巡店使用稳定终态时间，退款使用独立结算时间；线程收养、编辑、
  删除/恢复不会把旧交付搬到今天。巡店关联 task 的任务量、失败、退款、
  成本、令牌和趋势精确合并一次，既不漏算也不跨行业重复。
- 看板按行业返回老板应关注的经营指标目录（如餐饮营业额、人工成本率、
  食材成本率、翻台率），未接 POS/ERP 时只显示“待接入”和所需数据源。
- 本期新增/处置和全部未关闭积压分开口径；跨租户查看时不返回会跳到
  当前登录租户路由的伪链接。
- 看板仅读取结构化状态、时间和计费头，不扫描任务正文、巡店结论、
  问题或整改正文。未接 POS/ERP 的营收、利润、ROI 等指标显式为
  `availability=false`，不生成假数据。

## schema51 与横向加固

- 新增 `tenant_industry`、`task_thread`、`store_branch`、
  `inspection_visit/photo/issue/evidence/action/recheck/event` 表及相关作用域、
  幂等、并发和看板索引；`PRAGMA user_version` 与迁移账本均为 51。
- schema50 的明确 `industries_json` 映射在升级时写入
  `tenant_industry`，包括升级当时被停用的租户；空映射在运行期
  fail-closed，不再被解释成“全行业”。
- 用户/租户停用与 session 撤销放在同一写事务内，登录解析同时校验用户
  和租户的启用状态；撤销 epoch 使用单条原子 UPSERT 累加，并发撤销
  不会丢更新，重新启用也不会让旧 Cookie 复活。
- 任务中心和全部受管文件读取都补上 tenant + server-authoritative
  module/industry 过滤；同租户跨模块、跨行业，以及命名 Boss 跨租户直接
  打开正文附件均 fail-closed。owner 的行业映射被撤销后，旧巡店照片链接也立即失效。

## schema52 实施增量

日期：2026-08-10

状态：候选树功能与留存 v2 已实现；待最终独立复审、最终回归和不可变构建

### 门店主数据与批量导入

- 新增规范 XLSX 模板、受限解析、只读预览和原子提交。门店以
  `tenant + industry + store_code` 为稳定更新键，支持店号、店名、区域、地址、
  店长等字段；坏行定位、显式跳过、请求键与源文件哈希幂等、commit CAS 和并发
  重放均由服务端约束。
- 门店列表增加编号/名称搜索、区域筛选、稳定游标和固定响应上限；导入成功后，
  巡店人员可从企业门店列表勾选，不再重复手工建店。
- XLSX 入口拒绝宏、外链、公式、超预算 ZIP/XML、超行/超单元格与异常有限数值；
  暂存字段经过加密，错误与回显对手机号等个人信息脱敏。

### 行业巡店标准、采集与经营数据

- 现有 11 个行业均有版本化标准目录；每条标准记录 mandatory/recommended/
  operations 层级、来源、生效时间、辖区和适用条件。企业、区域、门店覆盖采用
  显式作用域，适用强制项不能被无痕关闭。
- 每个行业返回 7 个有界采集槽位与拍摄建议，巡店照片绑定
  `capture_slot + item_code`；创建巡店时冻结 effective template snapshot，后续
  标准升级不改写历史证据。
- 销售、员工、客流、库存/损耗等进入结构化 observation/business-value 通道，
  带期间、单位、来源、可用性及不可用原因；视觉模型不接收经营表、员工 PII 或
  任意工作簿正文。
- 前端巡店工作台顶部提供“批量导入门店”，串联模板下载、上传、预览、确认、
  错误定位和导入后的门店筛选；巡店创建页按行业展示采集进度与经营指标。

### 留存 v1 终审发现与 v2 修复

- 第一版仅在租户再次请求时惰性清理、每次最多 8 条，导致不活跃租户超过 24 小时
  的加密预览仍可解密并进入备份；已提交导入还永久保留最多 60,000 条逐行 staging，
  相同满量导入会让数据库持续线性增长。这两项被独立评审定为 P1，未带病发布。
- v2 在应用启动和调度周期执行跨租户、有界 sweep，并保留租户请求路径的快速惰性
  清理；retention partial index 让扫描只触达尚未清理的到期候选。
- 提交时将完整 row action 与脱敏 payload 组成规范化内容，生成 SHA-256 内容地址，
  zlib 压缩后写入共享审计归档；归档写入后立即回读校验哈希、大小、行数与结构，
  验证通过才在同一事务删除重复 working rows。
- 导入账本长期保留计数、源文件元数据、目录版本、摘要、操作者、时间和归档坐标；
  归档可去重且被篡改时 fail-closed。任何清理都不触碰门店、经营值、巡店、问题、
  整改或账务等权威业务表。
- 大批量提交保持批量 SQL 与版本 CAS，不退化为逐行 CAS；新增留存测试覆盖跨租户
  有界清理、权威数据不变、内容寻址去重、归档篡改拒绝和重复满量导入增长边界。

## schema53 实施增量

日期：2026-08-12

状态：行业决策员工 V2 实现完成；QA 与独立终审进行中，尚未构建、未授权、未部署

### 行业决策目录与在岗口径

- 10 个非餐饮行业均已落地 6 名不复用岗位名的专属决策员工，共形成 10 份行业
  JSON、60 个行业痛点、64 条来源和 180 项结构化指标；餐饮原有 60 名员工保持不变。
- schema53 active 口径为 131 名：11 名核心员工、60 名餐饮员工和 60 名非餐饮
  V2 员工。schema52 的旧 360 名非餐饮模板员工进入 legacy，只服务历史任务、线程
  与会议，不再进入新派活、会议选人、进修或专家推荐。

### 冻结身份与历史隔离

- 任务、线程和会议在数字 `idx` 之外冻结五字段身份：员工 key、目录版本、名称、
  部门和规格 SHA-256；同一 `idx` 只有完整身份严格一致才可解析，缺字段、错字段、
  跨目录碰撞或伪造快照均 fail-closed。
- active 与 legacy 使用服务端权威解析；legacy 只读展示并可完成既有协作链，不能被
  重新派活。public task guide 只暴露安全的填写引导，private employee contract 只在
  服务端执行，不随公开员工详情或任务引导下发。

### V2 决策证据与交付门禁

- V2 public guide 为每名决策员工返回固定 `evidence_requirements`；客户端只提交
  `input_id/content/source_name`，服务端依据租户、冻结员工规格和内容生成并持久化
  `user_submitted_unverified` 证据 manifest，客户端不能指定证据 ID 或伪造 manifest。
- 单项证据正文最多 4,000 字符，全部正文与来源名合计最多 20,000 字符；首轮 create、
  followup 合并、完整 manifest 幂等比较和超限校验使用同一服务端合同。证据只进入
  用户提示区，不进入系统提示，也不被发送到外部研究查询。
- V2 交付执行严格决策门禁：缺项、引用未知、引用结构不完整或证据冲突时强制 HOLD；
  GO 只表示结构化覆盖与引用合同完整、可以进入人工审批，不表示材料真实且不得自动
  产生外部副作用。餐饮及其他 V1 员工继续使用原有任务合同和交互，不受本门禁改写。

### 不可变发布约束

- release builder 已将 `data/industry_decisions` 映射为不可变制品中的
  `config/industry_decisions`；发布前置检查重新验证 manifest 结构、目录树、文件
  SHA-256 和磁盘内容，并拒绝危险副作用描述或不一致的签名 payload。
- 本节只证明共享候选树的 schema53 实现事实。生产仍运行 schema52；在 QA、独立
  终审、不可变构建和新的明确授权完成前，不得构建或部署 schema53。

## schema54 实施增量：360 名原员工全部 current

日期：2026-08-13

状态：V3 目录、岗位版本身份、运行时接线和最终本地验收已完成；未构建正式 release、
未取得部署授权、未部署

### 在岗花名册与岗位版本

- 非餐饮原 360 名员工全部保持 `current`、在岗并沿用原 `idx`：十行业各 36 名，
  号段仍为 `1001–1036`、`1101–1136`、…、`1901–1936`。加餐饮 60 名后，行业
  active 为 420；再加核心 11 名，总现役为 431。
- V1 的同 `idx` 360 份定义和 V2 的 `20xxx` 60 份定义只是不再承接新任务的
  **历史岗位版本**，不是历史员工、退役员工或降级员工；它们只为旧任务、线程与
  会议提供精确复现。员工本人仍以原工号对应的 V3 current 岗位承接新任务。
- 运行时把人员状态、岗位版本状态和任务连续性分开：当前岗位可新派活，历史岗位
  版本只可沿原任务链继续；“交给当前岗位重新做”必须创建新的根任务和计费边界。

### 360 份真实岗位合同

- 每个 V3 岗位都落有独立专业档案、唯一主决策和四维优先级。四维为痛点强度、
  发生频率、经济价值、数据可得性，用于选择高价值、高频且可执行的问题，而不是
  为凑人数复制通用岗位。
- 每岗合同完整覆盖：专业范围与行业知识、真实数据对象、必需 inputs、专属 workflow、
  outputs、只读 tools、skills、capabilities、升级矩阵、learning 路径，以及 3 个带
  公式、窗口与数据源的行业原生 KPI。岗位名、提示词、技能或流程的单字段替换均不能
  通过结构与语义门禁。
- 十行业按 8 个痛点簇组织，共 80 个痛点簇、360 个岗位。来源不只校验“URL 存在”，
  还由独立审阅者逐簇核对发布者、适用范围以及 source→pain→role 的语义支撑关系；
  错引法规、以会计资料支撑价格公平等语义错配均作为阻断项修复。

### schema54 身份、配置与连续执行

- `employee_slot` 保存稳定员工槽位、当前 `identity_ref`、启停状态和 `row_version`；
  `employee_role_config` 按完整岗位身份保存 prompt、skills、capabilities、settings、
  model、`config_revision` 和配置 SHA-256，历史岗位配置不会按 `idx` 泄漏到当前岗位。
- task、task_thread 和 meeting 冻结 full identity、`config_revision` 与配置哈希；创建、
  retry、followup、会议执行和输出编辑都精确解析同一岗位版本。同 `idx` 不足以解析
  岗位，身份缺失、版本歧义、配置篡改或陈旧 CAS 均在执行/计费前 fail-closed。
- 目录写入权威源收敛为三个生成器：`generate_industry_decisions_v3_a.py`、
  `generate_industry_decisions_v3_hotel_fitness.py`、
