## 做对的事

- 没有把“CLI 带了 WebSearch 参数”当作联网成功，而是验证真实 tool use/result，
  零成功即失败关闭。
- 没有把模型口头说“权限不足”或空选题记为成功，热点结果增加了质量门。
- 没有为了提高线索召回放宽原帖安全门；结构化来源仍须经过详情路径、SSRF、
  逐跳终站、正文和标题对应校验。
- 没有把员工私有资料塞进公开检索或图片编辑提示；采用 private system、公开
  research brief 和“私有规划→泄露检查→公开执行”的分层设计。
- 每次失败都以真实生产任务验证，并检查终态退款、活动任务和待结算归零。

## 暴露出的系统性问题

1. **参数存在不等于能力执行。** 旧预检只证明 CLI 支持 `--tools`，无法证明
   无头模式真正获准并成功运行 WebSearch。
2. **模型返回不等于有效交付。** 热点空选题、权限声明曾被当作正常 JSON 保存。
3. **员工编号不等于员工能力。** 多个工具原先只按员工索引选择模型，没有把
   工作方式、能力和技能库注入私有执行上下文。
4. **搜索召回不等于原帖。** 搜索页、账号页、聚合页、编码路径和跨站终跳都可能
   伪装成可点击来源，必须由服务端冻结和复验。
5. **可选增强不能拖垮核心资产。** hotfix5 已拿到严格核验原帖，却因最终画像
   模型超时丢弃整个任务；核心来源和可选分析必须分层。
6. **超时必须覆盖完整调用。** 单轮模型超时若不包含保密重写，实际墙钟可能翻倍；
   主备模型也必须用一次路由快照保证真正异模。

## 固化规则

- 联网任务以“至少一次成功工具结果 + 结构化来源/业务质量门”为成功条件。
- 可信 URL 只能来自结构化工具结果或受控公开发现源，不能来自模型自由文本。
- 任何线索先验证、冻结来源，再做画像和话术；增强失败可保守降级，但不得编造。
- 所有员工型 AI 调用必须显式走私有上下文封装；确定性渲染、URL 校验等非 AI
  动作除外。
- 发布必须经过全量测试、不可变制品、隔离 wheelhouse/venv、备份恢复演练、

## 这次新增的系统性教训

1. **模型名不等于视觉能力。** 文本模型接受 `image_url` 并返回 JSON，不代表它
   看过像素。视觉调用必须由目录能力字段 fail-closed 路由，并以真实像素 canary
   证明，而不是以 HTTP 200 证明。
2. **合法 JSON 不等于有效巡店。** 100 分、0 问题若没有逐图覆盖、可分析性、
   可见事实和异模复核，仍是假阴性；不得写成完成或计费成功。
3. **静态样例会污染动态外键。** 员工模板里固定 `photo_id=1` 会和运行时真实图片
   ID 冲突。最终权威合同必须在所有可编辑模板之后，并动态绑定 allowed IDs/count。
4. **韧性不能变成编造。** 可以规范百分比、布尔字符串等表现差异，但不能推断
   photo_id、补证据、补负责人或补期限；缺失字段应触发有界格式重做。
5. **健康检查不能替代业务验收。** hotfix7、hotfix8 的服务、HTTPS、模型调用都
   正常，但真实巡店分别出现假阴性和合同失败。只有原图复用后得到可追溯问题、
   证据与整改动作，才算通过。
6. **诊断也必须尊重不可变 release。** root Python 若未使用 `-B` 和
   `PYTHONDONTWRITEBYTECODE=1`，会在活跃 release 生成 `__pycache__` 并破坏固定
   materialized 证据。生产诊断必须禁止写 bytecode，并在结束后复查 manifest。

## 新固化规则

- 模型目录显式登记 `supports_vision`；任何未验证模型不得进入视觉路径。
- 每张照片必须有唯一动态 ID、逐图 review、非空可见事实与置信度；问题证据只能
  引用本次可分析照片，零问题必须由不同视觉模型复核。
- 合同错误最多同模重做 1 次，且主调用、重做、异模复核共享绝对墙钟；原输出不
  回传、不记录。供应商错误、泄露、取消和语义硬门不借格式重做绕过。
- 生产业务 smoke 使用固定幂等号和 exactly-once 写；响应不确定只查权威锚点，
  不换 key、不补发。失败即停止并保留审计。
- 每次交付都要同时证明：不可变发布证据、运行健康、账务归零、真实业务产出、
  权限边界和无敏感内容泄露。

## schema52 发布复盘

本节记录已闭环的工程教训；schema52 已于 2026-08-11 通过固定升级器上线，最终
release、回执与线上证据见 `11-release.md`。

### 暴露出的留存问题

1. **有 TTL 配置不等于数据会按时消失。** 只在租户再次访问时惰性清理，会让不活跃
   租户的加密预览无限期留在在线库和备份中；定时生命周期必须跨租户、可推进且有界。
2. **加密不等于可以无限留存。** 暂存虽然没有 PII 明文，但密文仍是可解密个人信息，
   超过业务必要期仍应删除工作明细并留下最小审计摘要。
3. **提交成功不等于 staging 可以永久存在。** 一次满量导入可产生 60,000 条逐行记录，
   重复导入会线性放大数据库；工作副本与长期审计资产必须分开。
4. **压缩不等于可审计。** 归档必须包含完整 action 与脱敏数据，规范化后内容寻址，
   并在删除 working rows 前验证哈希、大小、行数和结构；损坏时必须 fail-closed。
5. **清理不能误伤业务真相。** 门店、经营数据、巡店、问题、整改和账务是权威记录，
   留存事务只能删除可重建的导入工作明细。
6. **安全修复也要守住规模。** 周期 sweep 使用 partial retention index 与批次上限，
   提交继续使用 batch CAS；不能用逐行 CAS 把 60,000 行安全地“修慢”。

### 新固化规则

- 所有临时数据功能都必须同时回答：谁触发清理、无请求时谁清理、每批上限、索引、
  重试推进、备份暴露窗口和永久保留字段。
- 长期审计采用“永久摘要/摘要哈希 + 可验证脱敏归档”，不默认保留在线工作副本；
  归档写入、验证和工作明细删除必须在同一事务边界内。
- 数据生命周期测试必须覆盖不活跃租户、跨租户公平推进、重复最大批次、归档去重、
  篡改拒绝、权威表不变和进程重启后的周期执行。
- 用户授权部署只打开执行权限，不自动放宽 P0/P1、回归、不可变构建、回滚和正式域名
  业务门；发布证据不全就保持旧版本在线。
- postdeploy 诊断同样属于发布攻击面：本次独立脚本漏加 `-B`，在 current release
  生成 4 个 manifest 外 pyc，materialized/bootstrap 因此按设计转红。缓存目录经
  精确核验后整棵同盘隔离并保留 inode/SHA，固定证明恢复全绿。此后所有活跃/候选
  release Python 诊断必须同时设置 `PYTHONDONTWRITEBYTECODE=1` 与 `-B/-I`；发现
  manifest 外条目先 BLOCK、归因、可逆隔离和重验，禁止静默删除或忽略。
