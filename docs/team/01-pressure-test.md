# 需求压力测试

结论：**强需求，进入完整通道。**

## 为什么不是“再加三个页面”

- 巡店结果若没有整改责任、期限和复查，只是一份不可执行的图片点评。
- 数字员工若只交付第一版，老板仍需转到微信或线下反复解释，平台没有形成工作闭环。
- 看板若只堆任务数，没有行业范围、风险和下一步动作，就不能支持老板决策。

## 最危险的失败方式

1. 视觉模型看不到照片却输出确定性结论。
2. 整改项与照片证据脱钩，复查无法证明是否解决。
3. 第二轮从旧版本分叉，老板看到多个互相冲突的“最新版本”。
4. owner 借 tenant/industry 查询参数查看别人的经营数据。
5. 看板扫描业务正文或逐行 N+1，数据多后拖慢全站。
6. 没有 POS/ERP 数据时伪造营收、毛利、库存等经营指标。

## 反证与守护栏

- 巡店问题必须引用本次照片编号；模型无有效图片证据则失败收口，不生成虚假整改项。
- 复查只允许针对仍开放的整改项，保留整改前后照片与状态历史。
- 每条任务链只有一个可继续的最新叶子；历史版本只读，防止分叉。
- 所有聚合先固定 tenant，再固定授权行业；平台跨租户能力只属于命名 Boss。
- 看板只读 header/计数列，正文仅在用户点开具体产出时读取。
- 首版经营层只展示可证明的平台指标和明确的行业待接指标。

## 商业判断

巡店闭环把派活从内容工具扩展到线下经营管理；连续协作提高单个员工的完成率与留存；
老板看板让企业主看到数字员工的实际产值，是续费、扩员工和行业复制的直接承载面。

## 行业决策员工 V2 压力测试（2026-08-11）

结论：**现有十行业员工结构不通过真实性关口，必须重建，不能继续补文案。**

### 已坐实的反证

- 十个非餐饮行业均为 36 人；9 个行业的 36 个岗位名与汽车行业逐项相同，健身为
  35/36 相同。
- 旧生成/修复脚本和 `industryknowledge.py` 均明确承认这十个行业来自同一模板；
  现有知识层只能给通用岗位补行业术语，不能改变岗位正在作什么决策。
- 药房真正的硬门是药师审方、GSP、追溯码和医保基金风险；酒店是房晚易失库存、
  渠道净收益和房态翻台；把两者都叫“需求预测与补货计划”会误导老板选人。

### 最危险的失败方式

1. 只按 idx 原地改姓名和职责，却不版本化岗位配置，导致历史任务、员工自定义提示词、
   技能库和模型突然换语义。
2. 把 360 人压缩成 60 人，或为了补足 360 人机械复制岗位；前者违背在岗员工事实，
   后者制造职责重叠的空岗位。
3. 只更名不改 `required_inputs/evidence/approval_boundary`，模型继续凭通用常识交报告。
4. 把法规硬门、经营优化和增长实验揉成一个员工，最后既不能放行也不能算经营账。
5. 把行业报告的样本数据当作客户门店事实，或把地方规则冒充全国强制规则。
6. 新花名册只在列表隐藏旧员工，但 API 仍允许知道旧 idx 的客户端新建任务。

### 守护栏

- V3 保留原员工 idx，使用完整岗位 `identity_ref` 与配置 revision 区分同一员工的历史/
  当前岗位版本；旧岗位只服务既有任务和其合法后续轮次。
- 360 人全部在岗，但每个岗位必须有唯一主决策、独有输入/证据/输出和可计算指标；
  通用方法可以复用，岗位职责不得十行业换词复制。
- 每名员工必须声明决策合同；合同字段缺失、来源失效或硬门证据不足时 fail closed。
- 法规/强制标准、行业协会/上市公司经营证据、企业实际数据分层保存；数值都带来源、
  适用范围和时点。
- 新建任务、智能匹配、会议选人和老板看板只使用 active roster；历史详情使用 resolver。
