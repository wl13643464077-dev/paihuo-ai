# 派活 PaiHuo

**门店 AI 督导 + 获客助手。** 老板把活派给店员，AI 盯执行、验照片、催整改；
每天把该发的获客内容递到老板手上。

线上产品：[https://paihuo.ai](https://paihuo.ai)

技术栈：FastAPI + SQLite（单文件）+ 原生 JS 单页，单进程部署在一台服务器上。

## 主要功能（第 0–3 期升级后）

界面收成 5 个入口：**今天 / 派活 / 门店 / 获客 / 我的**。不同角色看到的内容不同：

### 老板

- **今天**：只放每天要看的事——待拍板的活、超时没做的清单、没整改完的问题；每天早上收到
  「老板早报」，含各门店排行和"今天发什么"。
- **一句话派活给店员**：说一句"明天之前把三号店冷柜除霜拍照"，自动对上门店和人，
  店员拍照交差，AI 先帮您看照片是否合格，您再一键通过或打回。
- **开闭店清单**：按行业自带开店/闭店/交班清单，可增删改；哪家店没做完一眼看到，要拍照的项必须拍。
- **巡店**：拍照上传就能巡店，AI 找问题、按严重程度扣分；整改直接派到人、到期催办，
  误报可作废（不扣分），看不清的照片只补拍那一张。
- **门店排行 / 老板看板**：按清单、整改、派活、巡店算分，看哪家做得好、哪家拖后腿。
- **提醒与升级**：截止前 2 小时提醒、到点提醒；超时 30 分钟升级给店长、超时 24 小时升级给老板；
  晚上 22:00–7:30 不打扰。企业微信群里可以 @ 到具体的人。
- **获客**：今日必发（朋友圈/小红书/点评文案）、私域日历、竞品盯梢、线索雷达；发之前免费查一遍
  广告法和违禁词；定时自动写好按时送到；一键进公众号草稿箱或发企业微信群；
  数字人口播视频（需勾选肖像/声音授权）。AI 生成的内容默认带"AI 生成"标识。
- **行业专家与多专家会议**：店里的事直接问、直接派；所有 AI 交付统一成
  「一句话结论 + 3 条行动 + 要留意」，全文默认折叠。
- **团队与门店分配**：给店长、店员开账号，指定每个人负责哪些门店。
- **上手与付费**：新老板首次登录有上手卡（选行业 → 填店铺信息 → 免费生成今天 3 条文案）；
  套餐页永远能看到参考价和"1 点能做什么"；可开通微信扫码付款、短信验证码登录。

### 店长

- 只看、只管分配给自己的门店（总监看全部门店）。
- 给本店店员派活、审核店员交上来的照片，打回要写原因。
- 巡店问题的整改推进、指派给店员；清单完成情况和门店排行。
- 店员超时没做会先升级到店长。

### 店员

- **店员手机版 `/staff`**：打开就是"我的待办"，按逾期 → 今天 → 其他排好。
- 拍照交差：手机直接拍，自动压缩、带服务器时间水印（不能拿旧照片冒充），断网有提示、可重试。
- 开闭店清单逐项打勾拍照；整改任务拍照复查。
- 截止前收到提醒，企业微信群里被 @。

### 平台管理员（root）

- 后台：模型供应商（可直连 DeepSeek / 通义千问 / 智谱 / Kimi / 火山方舟，联网查资料用博查搜索）、
  高风险功能开关（默认全关）、短信登录、微信支付商户配置、租户与点数管理。

### 运维与稳定性

- 单进程锁（防止多开重复扣点）、北京时间换日、数据保留期自动清理、后台循环心跳与
  `/healthz?deep=1`、统一看门狗（卡住的任务自动收口并退点）。
- 数据库 + 素材每小时备份，可选异地同步到 OSS/COS。

## 本地运行

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.lock.txt
# 空数据库第一次启动需要给 root 账号 boss 设一个密码（至少 12 位，含字母和数字）
CONTENTCREW_BOOTSTRAP_PASSWORD='换成你的本地密码1' ./run.sh
```

默认仅监听 `127.0.0.1:8899`，浏览器打开 `http://127.0.0.1:8899/login`。
运行数据写在 `data/`，其中的数据库、素材、备份和凭据均被 Git 忽略。

模型供应商凭据请在本地管理后台配置。不要把真实 API Key、Cookie、账号密码、生产数据库或
用户素材提交到仓库。

## 测试

```bash
install -d -m 700 /tmp/paihuo-tests-$USER      # 自己独占的临时目录
umask 077
TMPDIR=/tmp/paihuo-tests-$USER .venv/bin/python -m unittest discover -s tests
.venv/bin/python -m compileall -q app deploy
node --check static/app.js
```

**两个容易踩的坑**（不照做会报 `unsafe migration lock`）：

- 数据库迁移锁文件必须**归自己、权限 600**。测试会在临时目录里建很多临时数据库，
  所以必须先 `umask 077`，并且用**自己独占**的 `TMPDIR`（共享的 `/tmp` 里可能有别人留下的同名文件）。
- 如果仓库里的 `data/contentcrew.db.migration.lock` 已经存在且权限不是 600（比如被别的账号或
  默认 umask 建出来的），先删掉它再跑。

只跑一个文件：`-p "test_simple_deploy.py"`。浏览器行为测试需要
`.venv/bin/python -m playwright install chromium`。部署脚本的语法检查：
`bash -n deploy/simple/*.sh`。

每个 Pull Request 都会在 CI 上自动执行同等检查。

## 部署

两种方式，二选一：

1. **简易部署（推荐 1–2 人团队）**：一条命令发布、失败自动回滚，见
   [deploy/simple/README.md](deploy/simple/README.md)。
2. **不可变发布体系**：确定性构建制品、独立验证、固定运维代码，见
   [deploy/DEPLOYMENT.md](deploy/DEPLOYMENT.md)。

备份与恢复见 [deploy/BACKUP_RECOVERY.md](deploy/BACKUP_RECOVERY.md)。
从旧版本（数据库 v57）升级到本版本前，务必先读
[docs/UPGRADE_NOTES.md](docs/UPGRADE_NOTES.md)。

## 协作方式

1. 从 `main` 创建 `feature/*` 或 `fix/*` 分支。
2. 完成修改并补充测试。
3. 提交 Pull Request，说明影响范围、验证结果和回滚方式。
4. CI、代码审查和安全审查通过后才能合并。
5. `main` 只代表通过评审的产品源码，不会自动部署生产。

生产发布由项目所有者从已审核提交发布，完成备份、迁移、健康检查，失败即回滚。

详细规则见 [CONTRIBUTING.md](CONTRIBUTING.md) 和 [SECURITY.md](SECURITY.md)。
